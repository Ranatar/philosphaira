## 1. P0 --- README против фактического MFA

**РАССОГЛАСОВАНИЕ.** В README уже документированы
`POST /api/auth/mfa/enroll` и `/confirm`, но ниже всё ещё написано
«Починка на будущее: два маршрута ... плюс окно в панели». Маршруты и
клиентское окно безопасности уже существуют.

**Исправление:** удалить исторический абзац; CLI `enroll-mfa.mjs`
описывать только как операторское аварийное/bootstrap-средство.

## 2. P0 --- provenance: «нет» пока не отличается от «не указано»

**РАССОГЛАСОВАНИЕ.** `plan-next.md` требует различать «нет» и «не
указано», но `provenance` --- необязательная строка, а пустое значение
вообще не записывается.

Сейчас нельзя машинно различить: - источник ещё не искали/не указали; -
источник искали, но не нашли; - это собственная реконструкция; - прежний
источник признан неверным и удалён.

`// ...` решает только третий случай.

**Минимальное исправление:**

``` text
provenanceStatus:
  unspecified
  sourced
  editorial_reasoning
  source_not_found
```

Старые записи без поля = `unspecified`; `//` миграционно =
`editorial_reasoning`. `source_not_found` означает редакционное
состояние, а не доказательство отсутствия источника.

## 3. P0 --- provenance относится ко всей сущности, а не к конкретному утверждению

**НЕХВАТКА.** `provenanceDriftWarning` правильно предупреждает при
изменении текста без изменения источника, но технически остаётся одна
строка на сущность.

Это недостаточно для: - `description` против `extendedDescription`; -
связи: существование, тип, вес и описание; - философа: биографические и
содержательные утверждения.

**Этап 1:** документировать нынешнее поле как «общее основание текущей
редакции сущности».

**Этап 2:**

``` json
"provenanceEntries": [{
  "id": "...",
  "kind": "primary|secondary|editorial",
  "citation": "...",
  "locator": "...",
  "supports": ["description"],
  "note": "..."
}]
```

Сделать миграционный путь из старого `provenance`.

## 4. P0 --- `//` как тип основания слишком неявен

**ТЕХДОЛГ.** Тип данных кодируется пунктуацией текста. Это плохо
валидируется, усложняет импорт/экспорт и будущие виды источников.

**Исправление:** хранить `kind/status` явно; `//` оставить только как
backward-compatible shorthand.

## 5. P0 --- счётчик покрытия измеряет заполненность, а не доказательность

Текущий «С источником: X/Y» смешивает библиографические ссылки и
собственные основания `//`.

**Исправление:** после структурирования показывать раздельно:

``` text
Связи:
  библиографический источник 312
  основание редактора         74
  источник не найден          18
  не разобрано              1220
```

Не вводить «процент истинности/достоверности».

## 6. P0 --- provenance нужно явно проверить в review lifecycle

Поле технически входит в состояние сущности, но reviewer должен явно
видеть:

``` text
Источник:
  было: …
  стало: …
```

Если меняются и текст, и основание --- показывать рядом. Если текст
изменён, а источник оставлен, `provenanceDriftWarning` желательно
доводить и до review preview.

**Probe:** commit, меняющий только provenance → reviewer →
approve/reject → history → revert.

## 7. P1 --- одна строка 300 символов не является долговременной библиографической моделью

Минимально нужны отдельные:

``` text
kind
citation
locator
url
note
```

Не требуется сразу строить Zotero/CSL. Свободная `citation` может
остаться основной строкой.

## 8. P1 --- нет нескольких и конкурирующих источников

Одно утверждение может иметь первичный текст, исследования, источник
«за», источник «против», редакторскую оговорку.

Следующий уровень --- `provenanceEntries[]`; позднее возможно:

``` text
stance: supports | disputes | contextualizes
```

Но только после понятного UI.

## 9. P1 --- provenance пока не покрывает все содержательные объекты

Сейчас он есть у concept/philosopher/relation. Но интерпретацию графа
также задают relation types, веса, rubrics, traditions и формулы метрик.

**Приоритет:** relation types/семантика weights → metric formulas →
traditions/rubrics.

## 10. P1 --- observations метрик версионируются, формула остаётся кодом

Нужен registry:

``` text
metricId
formulaVersion
formulaFingerprint
humanDescription
assumptions
limitations
usesWeights
usesDirection
provenance
```

Изменение формулы без повышения версии должно ломать acceptance. Делать
JS-формулу браузерно редактируемой для этого не требуется.

## 11. P1 --- impact preview пока структурный, не эпистемический

Это правильно как первый этап: он считает каскады, потерянные связи,
изоляцию, компоненты.

Следующий безопасный шаг --- **dependency impact**, а не обещание
точного глобального пересчёта:

``` text
изменён relation type X
→ затронуто N связей
→ M метрик используют соответствующие свойства
→ сохранённые observations остаются привязаны к прежней graph version
```

## 12. P1 --- live update требует отдельного worker

README честно говорит: без `notify-worker` чужая правка не попадёт в
открытую страницу.

Следовательно `npm start` --- запуск web node, а не всей
многопользовательской process topology.

**Исправление:** production docs должны явно требовать два процесса:

``` text
web:           npm start
notifications: npm run notify-worker
```

Желателен health/readiness-индикатор отсутствующего/отставшего worker,
иначе live mode деградирует молча.

## 13. P1 --- порядок `data-changed` является скрытым контрактом

Недавнее исчезновение графа было вызвано порядком подписчиков: фильтр
выполнялся до нормализации endpoints D3.

Значит порядок --- семантика, но event bus его не выражает.

**Исправление:** явные фазы:

``` text
data:received
→ data:derived
→ graph:bound
→ filters:recomputed
→ ui:refresh
```

либо единый orchestrator.

## 14. P1 --- multi-tab одного пользователя требует отдельного probe

Проверить две вкладки одной session: - notification/unread; - один
pending commit в двух вкладках; - edit/delete в одной и stale save в
другой; - convergence graph version.

## 16. P1 --- plan/tree consistency ещё не покрывает всю документацию

`plan_probe` --- сильный механизм, но README/MFA показывает, что
историческая проза может устареть вне его признаков.

Не надо парсить всю документацию. Для операционно значимых фактов можно
иметь небольшой manifest и генерируемый status block.

## 17. P2 --- CSS-классы без собственного rule требуют визуальной классификации

Само отсутствие отдельного CSS rule не означает баг.

Для каждого подозрительного класса: 1. открыть реальное состояние; 2.
проверить computed style; 3. desktop/mobile; 4. решить, наследование
намеренное или правило забыто; 5. только затем исправлять.

Особенно server-only UI, которого offline sweep не видит.

## 18. P2 --- guest live updates требуют явной продуктовой политики

Если WebSocket только authenticated, guest видит изменения после reload.
Это не обязательно баг.

Нужно явно выбрать: - guest = snapshot/read-only; - либо read-only live
signal для guest без персональных payload.

## 19. P2 --- discussion thread пока не доказан необходимым

`authorComment + reviewComment + supersedes` уже покрывают обоснование,
решение и исправленную версию. Не добавлять чат до реальных случаев, где
этого недостаточно.

Если thread появится --- append-only и не заменяет обязательный
`reviewComment` при reject.

## 21. Definition of Done для provenance v2

Система должна без текстовых трюков различать:

``` text
A. Источник пока не указан.
B. Есть библиографический источник.
C. Это собственное аргументированное построение редактора.
D. Источник искали, но пока не нашли.
```

Для B возможен точный локус. Reviewer видит изменение основания в diff.
После изменения текста старый источник не становится молча
подтверждением новой формулировки.

История должна отвечать:

``` text
какой текст
какое основание
в какой версии
кто предложил
кто принял
когда
```

## 22. Вывод

Главные оставшиеся проблемы теперь находятся не в базовом запуске
сервера, а на границах:

``` text
документация ↔ фактический продукт
event bus ↔ скрытый порядок
web process ↔ worker
сущность ↔ конкретное утверждение
наличие строки источника ↔ эпистемический статус
замер метрики ↔ версия формулы
```

Их стоит исправлять раньше новых крупных функций.
