## Как поднять

Нужны Node.js, npm и PostgreSQL. Шаги 1–5 делаются ОДИН РАЗ, шаг 6 —
каждый раз.

### 1. База в правильной локали

```
createdb philos --locale=C.UTF-8 --template=template0
```

Голая локаль `C` не годится: единственность логина и почты держится на
`lower()`, а там `lower('ИВАН')` возвращает `ИВАН`. Проверяет `auth_probe`.

### 2. Зависимости

```
cd server && npm install
```

### 3. Окружение

`.env.example` — перечень переменных, а НЕ загружаемый файл: точки входа
читают `process.env` напрямую, `dotenv` в зависимостях нет.

```
export DATABASE_URL='postgres://postgres@localhost:5432/philos'
export MFA_SECRET_KEY="$(node -e "console.log(require('crypto').randomBytes(32).toString('base64'))")"
export BOOTSTRAP_ADMIN_PASSWORD='ваш-длинный-пароль'
```

Ключ второго шага сохраните: потеряете — потеряете все заведённые TOTP.

**Для открытой регистрации нужны ещё две переменные**, иначе она не
работает: подтверждение адреса идёт письмом, а без подтверждённого адреса
права срезаны.

```
export SMTP_URL='smtps://пользователь:пароль@smtp.поставщик.tld:465'
export MAIL_FROM='ΦilosΦaira <no-reply@ваш-домен>'
```

Не заданы — работник скажет об этом первой строкой при запуске и не будет
слать никуда. Домен `MAIL_FROM` обязан иметь SPF, DKIM и DMARC: без них
письма подтверждения уходят в спам, и сервис выглядит сломанным при
исправном коде.

**За обратным ставнем задайте `TRUST_PROXY`** (обычно `1`). При
`NODE_ENV=production` без него узел не поднимется — нарочно: за ставнем без
доверия ему `req.ip` равен `127.0.0.1` у всех, адреса в `user_sessions` и
`audit_log` перестают отвечать на вопрос «откуда заходили», а предел
регистраций бьёт по всем разом. Доверять всегда нельзя тоже: без ставня
любой присланный `X-Forwarded-For` станет «адресом человека».

### 4. Схема

```
npm run migrate
npm run migrate:status
```

Повторный накат безопасен: применяется только то, чего нет.

### 5. Семя графа и первый администратор

```
npm run graph:import
npm run bootstrap-admin
```

Перенос кладёт шесть наборов из `../app/data` в `graph_entities` и
работает ТОЛЬКО на пустом графе: `importSet` пишет с `ON CONFLICT DO
UPDATE`, и повтор перезаписал бы серверные правки семенем. Шесть JSON —
это семя, рабочее состояние живёт в базе. Осознанный повтор —
`ALLOW_GRAPH_REIMPORT=1`.

Первый администратор заводится только при пустой таблице и получает
НАСТОЯЩИЙ пароль. Почта помечается подтверждённой: оператор уже держит
`DATABASE_URL` и ключи — это доверие сильнее письма, и оно снимает круг
«чтобы настроить систему, нужен администратор, а чтобы он получил права,
должна работать почта».

ВТОРОЙ ШАГ САМ НЕ ЗАВОДИТСЯ: секрет должен увидеть человек, вносящий его
в приложение. До этого опасные права срезаны — включая `manage_admins`,
то есть **второго администратора не назначить, пока не заведён TOTP**.

### 5а. Заведение второго шага

```
POST /api/auth/mfa/enroll           → { секрет, ссылка, включён: false }
POST /api/auth/mfa/enroll/confirm   { code } → { включён: true, коды }
```

Оба хода требуют входа и признака CSRF. Имя берётся ТОЛЬКО из сессии: ни
`userId`, ни логин из тела не читаются вовсе — иначе всякий вошедший
заводил бы второй шаг чужой записи и запирал бы её на свой телефон.

Средство оператора остаётся на случай, когда в панель не войти:

```
node scripts/enroll-mfa.mjs [логин]      # умолчание — admin
```

Порядок нарочно двухтактный: секрет показывается, но шаг не включается,
пока не предъявлен код из приложения. Иначе можно запереть себя, сохранив
в базе секрет, который никуда не записан.

Коды восстановления выдаются в конце и видны ОДИН раз. Они одноразовые и
на случай потери аутентификатора; при обычном входе вводится код из
приложения — `submitCode` принимает оба, не различая, и потому код
восстановления легко потратить впустую.

### 5б. Первая раскладка графа

```
npm run relayout               # посчитать и ПОКАЗАТЬ меру расхождения
npm run relayout -- --применить
```

Раскладка — часть состояния графа, а не картинка клиента: считать её на
каждой машине нельзя, потому что один и тот же `d3` в разных движках даёт
разные координаты на одних данных (медиана расхождения 65 px). Если каждый
считает сам, у всех выходит своё, и общий язык про «вон тот сгусток справа»
пропадает.

Дальше раскладка **доращивается сама** при каждом утверждённом коммите,
задевающем состав узлов или связей. Полная перекладка нужна редко: дорасклад
накапливает след, и раз в долгое время картину полезно переучредить.

**Ход двухтактный нарочно.** Без `--применить` программа только считает и
показывает меру: медианный сдвиг узла, сколько узлов уехало дальше 200 px и
кто дальше всех. Это число решения — при медиане порядка сотни пикселей
пространственная память людей о графе перестанет работать. Прежняя раскладка
хранится, откат — `npm run relayout -- --откат <номер>`; но откат вернёт
координаты, а не спокойствие, и потому лучше посмотреть меру заранее.

### 6. Запуск

```
npm start                # http://127.0.0.1:8814/
PORT=9000 npm start
```

Один узел поднимает разом страницу, API и живые соединения. Запуск НИЧЕГО
НЕ ГОТОВИТ: не накатывает миграций, не сеет граф, не заводит людей —
молчаливая подготовка при старте есть способ однажды перезаписать рабочую
базу. Останов по `Ctrl+C`: закрываются соединения, потом пул.

При `NODE_ENV=production` включаются cookie только по HTTPS, значит нужен
обратный ставень с TLS.

### 6а. Что видит гость

Гость (не вошедший) получает СНИМОК: граф на миг открытия страницы. Живых
обновлений у него нет — сокет ему не открывается вовсе, и чужие правки он
увидит после перезагрузки.

Это решение, а не упущение: по сокету идут не только правки графа, но и
личные извещения, а развести их — отдельная работа. Пока они не разведены,
всякий сокет несёт то, что гостю знать незачем: кто что правит, чьи правки
ждут рассмотрения.

### 7. ДВА ПРОЦЕССА, А НЕ ОДИН

```
web:           npm start              # страница, API, сокеты
уведомления:   npm run notify-worker  # доставка извещений
```

**`npm start` ПОДНИМАЕТ УЗЕЛ, А НЕ ВСЮ СИСТЕМУ.** Работник исходящих —
отдельный процесс, и без него цепочка обрывается на первом же звене:
коммит кладёт извещение в исходящие, работник публикует его в шину, узел
рассылает по сокетам, страница берёт приращение. Нет работника — нет
второго звена, и **чужая правка не доходит до открытых страниц вовсе**.

Хуже всего, что это НЕ ВИДНО. Сервер отвечает, страница работает, правки
сохраняются; молчит только живое обновление, и заметит это второй человек,
а не тот, кто разворачивал. Один пользователь не увидит беды никогда.

При развёртывании поднимайте оба и следите за обоими: `systemd` — два
юнита, `docker compose` — две службы. Останов работника по `Ctrl+C` или
`SIGTERM`, доработав текущую порцию.

ПОКАЗАТЕЛЯ ОТСТАВШЕГО РАБОТНИКА ПОКА НЕТ — если исходящие копятся, узнать
об этом можно только запросом к базе:

```sql
SELECT count(*) FROM outbox WHERE delivered_at IS NULL;
```

Растущее число значит, что работник стоит или отстал.

### Что сделано против спама — и чего не сделано

Две вещи, и обе в коде:

- **Письма уходят только на ПОДТВЕРЖДЁННЫЕ адреса**, кроме самого письма
  подтверждения. При открытой регистрации выдуманных адресов много, письма
  на них возвращаются отказом, а доля отказов решает, попадут ли все письма
  домена в спам — включая подтверждения, без которых регистрация мертва.
- **Отписка одним нажатием** (`src/notify/unsubscribe.js`): у рассылок есть
  заголовки `List-Unsubscribe` и `List-Unsubscribe-Post`, ход
  `POST /api/notifications/unsubscribe?u=…&t=…` работает без входа и без
  признака CSRF — его присылает почтовая служба, а не браузер. У писем
  обязательных категорий («моя учётная запись», «моё положение») заголовка
  нет: отписка, которая ничего не выключает, хуже её отсутствия.

**Остального код сделать не может.** SPF, DKIM и DMARC заводятся у домена, а
не здесь; без них письма уходят, но в спам, и служба выглядит сломанной при
исправном коде. Проверять не глазами: пошлите письмо на ящик крупной службы и
посмотрите в заголовках `Authentication-Results`.

### Два рода отказа почты

Постоянный отказ (`5xx`, негодный конверт) и исчерпание попыток
(`MAX_ATTEMPTS`, десять) **закрывают строку исходящих**, а не возвращают её
в очередь. Иначе несуществующий адрес — при открытой регистрации их будет
много — повторялся бы раз в час вечно и отравил бы счёт выше, то есть
единственный признак отставшего работника. Временный отказ (`4xx`, сеть,
срок) откладывается с растущей задержкой, как прежде.

Закрытая безнадёжная строка отличается от доставленной тем, что у неё
осталась ошибка:

```sql
SELECT count(*) FROM outbox WHERE delivered_at IS NOT NULL AND last_error IS NOT NULL;
```

Растущее число здесь значит другое: адреса, на которые письма не доходят
никогда. Признак в самом
продукте — записан как незакрытое (`doc/plan-next.md`, этап F).

## Приёмка

`bash accept.sh` — или `bash ../tools/accept.sh` вместе с приложением.
Проба почты (`probes/mail_probe.mjs`) базы не требует и идёт первой.
Приёмка проверяет устройство и НЕ ЯВЛЯЕТСЯ ЧАСТЬЮ ЗАПУСКА: она сносит
`philos_test` до пустого места, и гонять её на рабочей базе нельзя.

Что стережёт каждый слой и почему слоёв столько — в `doc/server-design.md`.
